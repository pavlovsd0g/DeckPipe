# Автообновление DeckPipe на Windows

Дата исследования: 16 сентября 2026. Статус: оценка, внедрение не начато.

## Рекомендация

Добавить штатный Tauri Updater: приложение проверяет новую версию, показывает изменения и кнопку «Скачать и установить». Установка начинается по согласию пользователя после завершения загрузок и операций Rekordbox. Самостоятельный установщик обновлений для этой задачи не нужен.

Tauri поддерживает обновление Windows через установщик и статический JSON с версией, ссылкой и подписью. Перед установкой приложение закрывается; есть hook для подготовки к выходу. Режим `passive` показывает прогресс установки. [Документация Tauri Updater](https://v2.tauri.app/plugin/updater/).

## Подпись и расходы

Подпись пакета обновления обязательна для Tauri. Пара ключей генерируется локально, публичный ключ встраивается в приложение, закрытый используется при подготовке релиза. Покупка сертификата для этого не требуется. Потеря закрытого ключа нарушит цепочку обновлений, поэтому нужен защищённый резервный экземпляр. [Подпись обновлений](https://v2.tauri.app/plugin/updater/#signing-updates).

Это отдельный механизм от Authenticode — подписи издателя Windows, от которой владелец DeckPipe отказался. Бесплатная подпись обновления не убирает предупреждения Windows об неизвестном издателе. [Подпись Windows](https://v2.tauri.app/distribute/sign/windows/).

Файлы можно размещать в GitHub Releases; отдельный сервер для открытых пакетов не нужен. GitHub ограничивает отдельный файл размером менее 2 GiB, но не устанавливает общий лимит размера релиза и пропускной способности загрузок. [Ограничения Releases](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases).

Моя оценка обязательных дополнительных расходов при локальной сборке и открытой раздаче пакетов через GitHub: **$0 в месяц**, без учёта труда разработчика, интернета и существующего компьютера. Если собирать через GitHub Actions, доступные минуты и оплата зависят от тарифа и типа runner; это отдельное необязательное решение. [Тарификация Actions](https://docs.github.com/en/billing/concepts/product-billing/github-actions).

## Доступ к пакетам

Исходники и пакеты не обязаны иметь одинаковую доступность. Если исходный репозиторий закрыт, можно согласовать отдельный открытый репозиторий только с установщиками. Для закрытых release assets требуется авторизация: нельзя зашивать общий GitHub-токен владельца в приложение. [Права на получение release assets](https://docs.github.com/en/rest/releases/assets#get-a-release-asset).

Если доступ к самим сборкам тоже должен оставаться закрытым, понадобится авторизация каждого пользователя или собственный endpoint, выдающий ограниченные ссылки. Это усложняет решение. Доступность текущего репозитория не меняем в рамках исследования.

## Что потребуется именно в нашем коде

Это выводы из текущего репозитория, а не готовая функция:

1. Подключить Rust/JS-компоненты updater и ограничить доступ к ним главным окном. Окна входа в сервисы не должны получать права на установку обновлений.
2. Добавить проверку версии, показ изменений, прогресс, повтор после сетевой ошибки и действие «Позже». Проверка при старте должна оставаться неблокирующей.
3. Перед установкой остановить очередь безопасным способом, дождаться очистки временных файлов, окончания записи в Rekordbox и освобождения backend. Простого закрытия окна для этого недостаточно.
4. Дополнить release pipeline генерацией `.sig` и `latest.json`, связать их с тем же проверенным установщиком и контрольными суммами. Сохранять предыдущие релизы.
5. Убрать привязку release-скриптов и части тестовых фикстур к единственной версии `0.6.0`: каждой новой версии нужен возрастающий SemVer. Один новый Git commit при неизменном номере версии для обычной проверки обновлений недостаточен.
6. Проверить обновление NSIS и MSI, сохранение профиля, авторизации и каталога, отказ UAC, нехватку места, оборванное скачивание, неверную подпись и повторный запуск после неуспеха. Нельзя незаметно переводить MSI-установку в NSIS.

## Сложность и оценка работ

Моя предварительная инженерная оценка, не фиксированная смета:

| Вариант | Работа | Дополнительная инфраструктура |
| --- | --- | --- |
| Только уведомление о версии и переход к установщику | 4–8 часов | GitHub Releases |
| Прототип встроенного обновления, один тип установщика | 12–20 часов | Открытые пакеты и ключ обновлений |
| Готовое решение для DeckPipe, NSIS + MSI, безопасное завершение операций и проверки отказов | **24–40 часов** | Обычно без отдельного сервера |
| Закрытая раздача с собственной авторизацией | Ещё 16–32 часа | Endpoint и обслуживание доступа; стоимость зависит от выбранного размещения |

Диапазоны альтернативные: часы прототипа уже входят в оценку готового решения. Сложность штатного варианта — средняя; основная работа связана с нашей очередью, двумя установщиками и сохранением состояния, а не с показом кнопки обновления.

Первую версию с updater пользователи установят обычным установщиком. Уже следующие версии смогут обновляться из приложения. Автоматический откат не считаем готовой возможностью: его потребуется отдельно спроектировать с учётом совместимости данных.
