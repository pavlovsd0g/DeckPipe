# DeckPipe — этап D: приёмка Windows private beta

Обновлено 16 сентября 2026 года. **Этап D завершён в объёме Windows private beta на текущем компьютере и профиле владельца.** Основные сценарии обоих стримингов, настоящего Rekordbox, установка MSI, NSIS lifecycle, физический USB и бюджеты производительности проверены. По прямым решениям владельца исключены другой Windows-профиль, выход/вход в Windows и подпись выпуска. Результаты на других конфигурациях Windows не заявляются.

## Производительность

Пять нативных запусков текущего кандидата: окно появлялось за 2,14–2,68 с, backend — за 2,00–2,09 с. Первый снимок мог содержать белую страницу: время полной отрисовки интерфейса этими цифрами не измерено. Рабочая память 496,79–518,67 МБ и приватная 277,47–288,18 МБ укладываются в бюджеты 650/1250 МБ.

**CPU gate пройден без активного инструмента управления окнами; лимит 100 мс за 2 с сохранён.** Первые пять запусков дали 93,8–156,2 мс и четыре превышения. Причина условий измерения подтверждена отдельным сравнением на одном и том же установленном MSI-процессе, с теми же десятью процессами в дереве и одинаковым хешем EXE:

| Состояние инструмента наблюдения | Пять измерений CPU за 2 с |
|---|---|
| Сеанс отключён | 0; 15,6; 0; 0; 0 мс |
| Сеанс подключён повторно | 140,6; 140,6; 156,2; 140,6; 140,6 мс |
| Сеанс снова отключён | 0; 0; 0; 0; 0 мс |

Все 300 проверок foreground подтвердили активное окно приложения; фактическое время каждого интервала записано. Отключение инструмента не перезапускало DeckPipe. Десять интервалов без наблюдателя прошли лимит. Независимое ревью подтвердило расчёт и границы вывода. Это проверка уже работающего окна, а не пять новых холодных запусков; конкретный внутренний механизм влияния Sky не установлен. Предварительная гипотеза о ненужных raw-input событиях проверена на двух диагностических сборках и не подтверждена; изменение `DeviceEventFilter` в продукт не внесено.

## Результат и границы приёмки

Установленная private beta `34a75a5` принята для текущего окружения. Семь файлов кандидата и точные payload обеих установок перепроверены. Из 889 файлов baseline перед MSI неизменны 888; единственное ожидаемое изменение — каталог SQLite после штатного сканирования. Настройки, зашифрованное хранилище входа, профили авторизации, настоящая база Rekordbox и пользовательская правка Orchestrator сохранены. [Итоговый checkpoint](<D:/DeckPipe-RC-Lab/qa-evidence/windows-stage-d-20260916/final-candidate-checkpoint.json>).

Подпись/timestamp исключены владельцем из требований выпуска. Текущая приёмка подтверждает NSIS update/uninstall/reinstall и MSI install/launch. Под прежней формулировкой «удаление MSI» подразумевалась деинсталляция самого DeckPipe, установленного через MSI, с проверкой регистрации Windows, сохранности музыки/пользовательских данных и повторной установки; этот сценарий отдельно не выполнялся. Удаление скачанного файла `.msi` не деинсталлирует приложение и не требует такого теста. Поддержка Rekordbox подтверждена на установленной версии 7.2.14.0323. Код CPU не менялся, поэтому пересборка принятого кандидата не требовалась. Merge, push и публикация не выполнялись.

Проверка отдельного стандартного Windows-профиля с кириллицей исключена владельцем 16 сентября: «мы не будем делать тест через новый профиль, делай все на этом». Позднее владелец также исключил проверку выхода/входа в Windows. Эти сценарии сняты с требований, а не отмечены как успешно проверенные. Сохранение сессий после перезапуска приложения и NSIS-переустановки проверено.

## Сохранённые неудачные проверки

Первый gate popup-кандидата остановился из-за запущенного Rekordbox; первый gate 34a75a5 запускался через Windows PowerShell5 и остановился на штатном stderr unittest. Принят отдельный полный прогон через PowerShell7. Первый реальный RB-сценарий не начал запись из-за проверки Conhost; следующий принял REUSE/откат и остановился до MEDIA на пустом ContentID проверочного кода. MEDIA выполнен отдельным успешным прогоном. Сценарий мутации/восстановления предварительно прошёл 11 проверок отказов и независимое ревью.

Первый NSIS lifecycle-readback увидел оставшийся registry key сразу после завершения родительского uninstall-процесса. Его дочерний процесс завершил удаление позже; повторное чтение подтвердило отсутствие файлов и регистрации, затем выполнена проверенная переустановка. Исходный FAIL сохранён рядом с успешным follow-up, ожидание в проверочном скрипте исправлено.

Исторические кандидаты, отчёты и неудачные запуски не перезаписывались. Старые checkpoint с недоступным управлением ПК устарели: нативная автоматизация работает. Доказательства находятся в `D:/DeckPipe-RC-Lab/qa-evidence/windows-stage-d-20260915` и `windows-stage-d-20260916`.

Первая фоновая попытка MSI завершилась кодом 1602 до установки; ожидающего UAC больше нет. Её исторический отчёт заменён по актуальности проверкой последующей ручной установки в `E:\DeckPipe`. Нативный инструмент управления блокирует интерфейс `msiexec.exe`, поэтому мастер прошёл владелец.
