# DeckPipe: единый вход через постоянный браузер приложения

Пользователь 14 сентября прямо одобрил единый встроенный метод для Deezer и SoundCloud и поручил реализацию. Это решение заменяет прежний приоритет внешнего браузера и условный статус WebView2. Повторное согласование не требуется.

## Результат для пользователя

Одна кнопка подключения сервиса открывает отдельное окно DeckPipe с настоящей HTTPS-страницей входа сервиса. Окно использует постоянный профиль этого сервиса. Уже действующая сессия в нём позволяет переподключиться без повторного пароля. Первоначальный профиль не наследует сессию обычного браузера. Расширения, Mozilla/AMO, браузерная регистрация native messaging и внешний OAuth не нужны.

Закрытие окна, отмена попытки, истечение пятиминутного ожидания, перезапуск и обычное обновление приложения не удаляют профиль или уже сохранённую авторизацию. Временные сетевые ошибки не означают выход. Отозванная сервисом сессия требует повторного входа; сроки cookies не подделываются и бессрочная авторизация не обещается.

Явный «Выйти и забыть вход» удаляет локальную авторизацию выбранного сервиса и данные его встроенного браузера, сбрасывая связанные кэши. «Сменить аккаунт» последовательно забывает прежний вход и запускает новый. Музыка и другой сервис сохраняются. Ошибка очистки должна быть показана, а не выдана за полный выход.

## Архитектура и границы

- Windows x64, Tauri 2.11.5 / Wry 0.55.1, текущий Python backend и Windows DPAPI. Зависимости и провайдерские загрузчики сохраняются.
- Профили: `%LOCALAPPDATA%\DeckPipe\AuthBrowser\deezer` и `%LOCALAPPDATA%\DeckPipe\AuthBrowser\sc`. Путь стабилен относительно версии и папки EXE; общий интерфейс приложения использует отдельный профиль. На рабочих профилях ничего не тестировать и ничего из них не импортировать.
- WebView2 создаётся через async/отдельный поток с `.data_directory(profile)` и `.incognito(false)`. Встроенные расширения и дополнительные разрешения удалённой странице не включаются. Недоверенные окна не получают Tauri-команды основного окна или токены backend.
- Стартовые URL фиксированы в Rust: `https://www.deezer.com/login`, `https://soundcloud.com/sign-in`. Внешняя страница не должна переходить к `file:`, `tauri:`, loopback backend или исполняемым схемам. HTTPS-переходы, необходимые для входа/2FA, допустимы. Popup либо получает тот же профиль и те же ограничения, либо явно безопасно отклоняется; нельзя молча открыть небезопасный внешний канал или наделить popup правами main.
- Cookie читается только нативным кодом из своего выбранного профиля через `cookies_for_url` точного origin сервиса, с проверкой имени и домена (`arl` для Deezer, `oauth_token` для SoundCloud). Нет чтения всей базы cookies, JS-инъекции для сбора паролей или возврата credential в frontend/URL/логи.
- Проверка сессии и транзакционное DPAPI-сохранение остаются в Python `AuthService` через существующие приватные маршруты `complete`, `commit`, `discard`, `logout`, `status` и оба bearer-секрета. Подтверждение приходит в UI только как безопасный статус и имя/ID аккаунта.
- Один активный вход, уникальная идентичность окна/попытки. Новая попытка, cancel, закрытие окна, expiry и logout исключают позднее сохранение старого результата. Cancel во время сетевой проверки не должен блокироваться до завершения запроса провайдера.
- Старая/невалидная cookie не закрывает окно раньше, чем пользователь сможет войти заново. Повторяется проверка изменившейся cookie; одинаковая отклонённая cookie не отправляется каждую секунду. Неопределённый таймаут, поздняя проверка и повторные validation rounds не могут допустить устаревший commit.
- Существующие сохранённые DPAPI-аккаунты принимаются без обязательного нового входа при запуске. Обычный restart не требует открытия окна. Профили WebView2 сохраняют cookies в рамках срока и правил сервиса; не добавлять неограниченный keep-alive или ручное продление срока.
- Полностью убрать extension/native-host runtime и их упаковку. Не запускать unregister против настоящего профиля: пользователь ничего не устанавливал в этой работе.
- Общая музыкальная папка, каталог, загрузчики, JSON/rename safety и этап A сохраняются. Этап C/Rekordbox и публичный выпуск D не выполняются. Не менять рабочую базу, реальные аккаунты, pin старого кандидата или изменённые пользователем файлы main.

## Контракт интерфейса

Сохраняются Tauri-команды `auth_begin(provider)`, `auth_status(requestId?)`, `auth_cancel(requestId)`, `auth_logout(provider)`. `auth_open_setup` удаляется. PublicStatus сохраняет `requestId`, `provider`, `status`, `expiresIn`, необязательные `account: {id,name}` и `errorCode`.

Статусы: `idle`, `waiting_browser` (ожидание в окне DeckPipe), `validating`, `connected`, `cancelled`, `expired`, `failed`. Поля `helper` и состояние `waiting_helper` удаляются. Общий status без requestId возвращает безопасную `accounts` карту как прежде и `authMode: "embedded"`. В UI нет упоминания расширений или необходимости ручного переноса токена.

## Приёмка

Проверки поведения: сохранённый профиль → тот же путь после restart/изменения каталога EXE; разделение провайдеров; cookie чужого сервиса/домена отвергается; невалидная старая cookie не мешает получить новую; повтор одной cookie не создаёт шторм запросов; cancel/expiry/logout/replacement во время проверки не допускают поздний commit; отказ очистки не даёт ложного успеха; успешный выход очищает только выбранный сервис; схема/loopback navigation и вызовы main-команд из login окон запрещены; в публичных ответах и логах нет синтетического credential sentinel.

Нужен реальный WebView2 probe с синтетической локальной страницей и отдельным профилем: persistent cookie и localStorage переживают полное завершение и повторный запуск процесса; очистка удаляет их; другой профиль сохраняется. Probe должен использовать производственную фабрику окна/профиля, не дублировать её настройки. Тестовая локальная страница доступна только отдельному example/test процессу и не создаёт runtime override для выпуска.

Полные Python/PowerShell-наборы, frontend build, Rust check/tests, независимое review, чистая сборка Windows из точной ревизии, чтение MSI без установки и изолированные проверки извлечённого backend. Реальные provider login/2FA и срок жизни аккаунта не объявляются проверенными по синтетике. В случае внешней границы подготовить работающую сборку и точный сценарий приёмки до обращения к пользователю.
